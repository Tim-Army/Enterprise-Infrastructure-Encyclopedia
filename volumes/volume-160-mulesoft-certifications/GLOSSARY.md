# Volume CLX — Glossary

| Term | Definition |
|:---|:---|
| **Anypoint Exchange** | The MuleSoft catalog/marketplace where APIs, connectors, templates, and reusable fragments are published and discovered — making the application network findable so teams reuse APIs instead of rebuilding. |
| **Anypoint Platform** | MuleSoft's unified integration platform — one environment to design, build, deploy, and manage APIs and integrations across their full lifecycle. |
| **Anypoint Studio** | MuleSoft's Eclipse-based desktop IDE for building Mule applications — assembling flows of connectors, transformations, routing, and error handling. |
| **API-led connectivity** | MuleSoft's central approach — structuring integration as reusable APIs in three layers (System, Process, Experience) that compose into an application network, replacing brittle point-to-point integration. |
| **API Manager** | The Anypoint component that governs APIs via a gateway — applying policies (rate limiting, OAuth security, SLA tiers, caching) without changing the API's code. |
| **Application network** | The web of reusable, discoverable, governed APIs connecting an organization's systems and data — the compounding asset that API-led connectivity builds. |
| **Catalyst** | MuleSoft's delivery methodology — a structured approach to delivering integration projects that achieve measurable business outcomes, emphasizing foundations and enablement; validated by the Catalyst Consultant certification. |
| **C4E (Center for Enablement)** | An operating model where a central team enables the rest of the organization to build on the application network (reusable assets, standards, coaching) rather than being a build-everything bottleneck. |
| **CloudHub** | MuleSoft's integration-platform-as-a-service (iPaaS) — a fully-managed cloud where Mule applications run, scale, and are monitored without managing infrastructure. |
| **Connector** | A pre-built Anypoint component for talking to an external system (HTTP, database, Salesforce, SAP, and 200+ others), so a Mule app reaches other systems without custom protocol code. |
| **DataWeave** | MuleSoft's functional transformation language — mapping and reshaping data between formats (JSON, XML, CSV, Java) with map/filter/field-mapping; distinctive to MuleSoft and heavily tested. |
| **Design Center** | The Anypoint component for authoring API specifications (RAML/OAS) and flows, with a built-in mocking service so a spec can be consumed before code exists. |
| **Experience API** | The top API-led layer — tailors underlying data for a specific consumer or channel (mobile, web, partner), reshaping the same process/system data per experience. |
| **Hyperautomation** | Extending integration into end-to-end automation by combining API-led integration with RPA (bots for no-API systems), IDP (extracting data from documents), and Composer (no-code integration). |
| **Mule application** | An integration built as flows executed by the Mule runtime — sequences of message processors (source, connectors, transformers, routers, error handlers) acting on an event. |
| **Process API** | The middle API-led layer — orchestrates and composes business processes across multiple System APIs, containing business logic independent of channel or backend. |
| **RAML / OAS** | API specification languages — RAML (RESTful API Modeling Language, MuleSoft-originated) and OAS (OpenAPI Specification) — machine-readable contracts defining an API design-first. |
| **Runtime Fabric** | The Anypoint deployment option for hybrid, on-premises, or private-cloud (including Kubernetes) — running the Mule runtime on your own infrastructure while managing it through Anypoint. |
| **System API** | The bottom API-led layer — unlocks data from a system of record (CRM, ERP, database) as a stable, reusable interface built once and reused by every process and experience above it. |
