# Chapter 36: Cisco IOS XE Router and FortiGate STIG Crosswalk

## Learning Objectives

- Explain why a FortiGate used as a router is assessed against the Router
  SRG, although FortiGate has its own NDM and Firewall STIGs.
- Align a Cisco IOS XE Router STIG rule with the FortiGate STIG rule, or the
  FortiGate setting, that implements the same SRG requirement.
- Use the Cisco IOS XE Router STIG rules as a working checklist for a
  FortiGate in a branch or SD-WAN routing role, and see where FortiGate
  meets, partly meets, or cannot meet each rule.
- Tell the six alignment categories apart and record each one correctly.
- Find the FortiGate STIG rules and SRG requirements that no Cisco router
  rule covers, so that the checklist covers both directions.
- Recognize which router rules reuse the verified Chapter 32 switch
  commands, which come from the router fix text, and how the router fix
  texts were corrected.

## Theory and Architecture

**The reference product is a Cisco router running IOS XE**, such as an ISR
4000 or a Catalyst 8000. Its STIG package has two STIGs: IOS XE Router NDM
V3R7 (42 rules, `CISC-ND-`) and IOS XE Router RTR V3R5 (97
rules, `CISC-RT-`), 139 rules in all
([Chapter 31](31-cisco-products-stigs-and-srg-mapping.md)). The RTR rules
apply by role: perimeter rules only to a router that connects an enclave to
NIPRNet or SIPRNet, PE and P rules only to an MPLS provider router,
out-of-band management (OOBM) rules only to an OOBM gateway, and BGP,
multicast, and MSDP rules only where those protocols run.

**The comparison product is a FortiGate used as a router**: the branch
router, SD-WAN edge, or enclave perimeter router that runs static routes,
OSPF, BGP, and multicast routing. FortiGate has two STIGs, the Fortinet
FortiGate Firewall NDM STIG V1R6 (`FGFW-ND-`) and Firewall STIG V1R5
(`FNFG-FW-`), 89 rules in all. **Neither FortiGate STIG covers
routing.** A FortiGate's routing functions are assessed against the Router
SRG, as [Chapter 10](10-fortinet-products-stigs-and-srg-mapping.md)
explains, and [Chapter 30](30-fortigate-feature-version-and-stig-map.md)
maps every FortiGate feature to the NDM and Firewall STIG rules and, for
routing, to the Router SRG requirements.

So this crosswalk mixes the two kinds of alignment in the earlier chapters.
For the NDM rules it is a **STIG-to-STIG pair**, like the Cisco ASA
crosswalk in [Chapter 34](34-cisco-asa-and-fortigate-stig-crosswalk.md):
36 of the 42 router NDM rules have a FortiGate NDM STIG
rule for the same SRG requirement. For the RTR rules it is a **STIG-to-SRG
alignment**, like the FortiSwitch crosswalk in
[Chapter 33](33-fortiswitch-and-cisco-catalyst-switch-stig-crosswalk.md): no
FortiGate STIG rule implements a Router SRG requirement, so each FortiGate
routing finding is recorded against the SRG ID. 36 of the
139 router rules have a FortiGate STIG rule; none of them is an RTR
rule.

### Why this is a crosswalk, and why the Router SRG

A STIG is a vendor-specific implementation of one or more SRGs
([Chapter 03](03-the-srg-catalog-how-stigs-are-built-and-what-to-do-without-one.md)).
Its rules carry their own check and fix text, and an assessor records a
finding against the rule. A crosswalk keeps that distinction:

- **The Cisco rule is a reference, not a requirement for FortiGate.** A
  FortiGate is never "compliant with `CISC-RT-000480`". It meets
  `SRG-NET-000230-RTR-000002`, the requirement that rule implements, and
  the FortiGate finding is recorded against that SRG ID on a Router
  SRG-based checklist. For the NDM rules with a FortiGate STIG rule in the
  FortiGate STIG rule column (`FGFW-ND-000300` for
  `SRG-APP-000001-NDM-000200`), the finding goes on the FortiGate NDM STIG
  checklist instead.
- **The SRG ID is the join key.** Two settings align because they implement
  the same requirement, not because they look alike. A Cisco `neighbor
  password` and a FortiGate BGP neighbor `password` align because both
  implement `SRG-NET-000230-RTR-000002`.
- **The FortiGate STIGs and the router STIGs cover different ground.** The
  router RTR STIG has no FortiGate STIG counterpart at all, and the
  FortiGate Firewall STIG has no router counterpart. Chapter 30 maps
  FortiGate features to 171 requirement IDs; 124 of them
  are cited by no router rule, including 54 of the
  89 FortiGate STIG rules and 4 Router SRG requirements. The
  second table in this chapter lists them.

### How the rules are aligned

Each router rule was aligned in four steps:

1. **Take the SRG ID the rule implements.** The rule ID, severity, SRG ID,
   and title come from the two IOS XE Router STIG XCCDF files
   (`U_Cisco_IOS-XE_Router_Y26M04_STIG.zip`). The 139 rules cite
   137 distinct SRG IDs.
2. **Look for the same SRG ID in the FortiGate STIGs and in Chapter 30.** The
   FortiGate STIG rule column comes from the FortiGate XCCDF files
   (`U_FN_FortiGate_Firewall_Y26M10_STIG.zip`): 36 router rules,
   all of them NDM rules, share an SRG ID with a FortiGate NDM rule.
   Counting the Router SRG requirements that Chapter 30 maps directly,
   49 of the 139 rules cite an SRG ID that Chapter 30 maps
   to a FortiGate feature (13 of them RTR rules).
3. **For the rest, read the requirement and find the setting.** The
   requirement text comes from the SRG XCCDF files (NDM V5R5 and Router
   V5R2). The FortiGate setting that meets it was found in the **FortiOS
   8.0.1 CLI Reference**. Where the reference has no such setting, the row
   says so.
4. **Judge how well the setting meets the requirement**, and assign one of
   the alignment categories below.

Two cautions apply to the alignment data:

- **CCIs were not used to match requirements.** Many SRG requirements share
  the catch-all CCI-000366 ("security configuration settings"), so a CCI
  match often links unrelated requirements. Every alignment rests on the
  SRG ID or on the requirement text.
- **Two router rules cite SRG IDs that are not in the current NDM SRG.**
  `CISC-ND-001030` cites `SRG-APP-000373-NDM-000298` (redundant time
  sources) and `CISC-ND-001470` cites `SRG-APP-000516-NDM-000351`
  (supported release); neither ID is in NDM SRG V5R5, and the current
  requirements for the same topics are `SRG-APP-000920-NDM-000320` and
  `SRG-APP-001035-NDM-000340`. The FortiGate NDM STIG cites the same two
  retired IDs (`FGFW-ND-000120` and `FGFW-ND-000170`), so the rows still
  pair.

### Where the commands come from

- **Cisco commands are reused from Chapter 32 where the rule is the same.**
  The IOS XE Switch STIGs share most rule IDs with the router STIGs, and
  [Chapter 32](32-cisco-catalyst-switch-feature-version-and-stig-map.md)
  checked every switch command against the IOS XE documentation and
  corrected the fix texts. A router rule reuses the Chapter 32 command when
  the switch STIG has the same rule ID **and** the same requirement text
  (compared after replacing "router" and "switch" with one word and
  ignoring articles and dash characters). 125 rules qualify,
  including `CISC-RT-000840`, whose switch title differs only by a DISA
  wording error ("Designated Cisco switch (DR)" for "Designated Router
  (DR)"). Where Chapter 33 trimmed a shared Chapter 32 command to the
  statements of one rule, the crosswalk uses the same statements. The build
  script checks that every reused statement appears in Chapter 32 for the
  same rule.
- **Two kinds of reused statement were adapted for routers.** Chapter 32
  writes `interface vlan <VLAN_ID>` (a switch virtual interface) for
  `CISC-RT-000010` and `interface vlan <USER_VLAN>` for `CISC-RT-000860`
  to `CISC-RT-000880`; the crosswalk uses `interface <L3_INTERFACE>`,
  which Chapter 32 uses for routed interfaces, in those 4 rows.
  Chapter 32's VTY ranges (`line vty 0 31`) follow the 32 VTY lines that
  Catalyst switches have by default from 17.1.1; on a router, check `show
  line` and apply the access class, timeout, and method list to every VTY
  line it has.
- **14 rules take their commands from the router fix text**:
  9 rules that the switch STIGs do not have (the alternate
  gateway rules `CISC-RT-000280` to `CISC-RT-000300` and the OOBM and NOC
  rules `CISC-RT-000400` to `CISC-RT-000460`), 4 rules whose
  router text differs from the switch text (`CISC-ND-001410`,
  `CISC-ND-001450`, `CISC-RT-000060`, and `CISC-RT-000780`), and
  1 rule whose Chapter 32 command is Catalyst-specific:
  `CISC-RT-000120` uses `cpp system-default`, the Catalyst 9000 default CoPP
  policy, where routers attach an MQC policy to the control plane. These
  commands were checked by a script, as Chapter 32 checked its own, against
  the saved Cisco documentation: the platform-independent **IOS XE command
  references for access and edge routers** (Security A to Z, Configuration
  Fundamentals, Embedded Syslog Manager, IP Routing BGP, OSPF, and
  Protocol-Independent, MPLS, QoS, Embedded Event Manager, and others) and
  the Catalyst 9300 26.x command reference and configuration guides. The
  script walks the IOS XE modes (interface, router, access list, route map,
  class map, policy map, control plane, ISAKMP policy, transform set,
  crypto map, VRF, and EEM applet). A statement passes when it is a
  documented command line in the same mode, when a command in a compatible
  mode has all of its keywords in its syntax or its syntax description, or
  when it appears word for word in the documentation. Of the
  113 statements, 69 matched a documented example,
  34 a command's syntax, 8 a command's syntax
  description, and 2 the documentation text. The script was tested
  with deliberately wrong commands (an undocumented hash and transform, the
  fix text's `snmp-trap` port name, a misspelled command and keyword, a
  wrong `service-policy` direction, and a wrong EEM action) and caught all
  of them.
- **FortiOS commands come from Chapter 30**, or from Chapter 34 for NDM rows
  with the same SRG ID, where the feature maps the same requirement, and
  otherwise from the **FortiOS 8.0.1 CLI Reference**. A script checked every
  FortiOS command against the 8.0.1 CLI Reference, as in Chapters 30 and 34:
  each `config` path must be documented, each nested `config` a documented
  sub-table, each `set` option an option of that path, and each literal
  value a documented value. It was tested with wrong commands (a misspelled
  path, `status off`, a VRF role `provider`, `spt-threshold infinity`,
  `hop-opt block`, and the FortiSwitchOS `ttl-security-hops` option) and
  caught all of them. The table has 274 FortiOS blocks in all,
  counting the second table.
- **MPLS on FortiGate was checked, not assumed.** The FortiOS 8.0.1 CLI
  Reference has no MPLS, LDP, RSVP, VPLS, pseudowire, or MSDP command. It
  does have BGP VPNv4 and VPNv6 address families and BGP VRFs with a `role`
  of `standalone`, `ce`, or `pe`, a route distinguisher (`rd`), and import
  and export route targets, and IPsec tunnels can carry VPN IDs with
  `encapsulation vpn-id-ipip`. A FortiGate can therefore act as a PE for
  BGP VPNv4 over IPsec overlays, but not as an MPLS PE or P router: the VRF,
  RD, and route target rules are **Partial**, and the LDP, RSVP-TE, VPWS,
  and VPLS rules are **Not supported**.
- Read the command cells as in Chapters 30, 32, and 34: each pair of
  backticks is one block, statements are separated by `;` to fit in a table
  cell (on the CLI, enter each on its own line), and values in
  `<ANGLE_BRACKETS>` are placeholders. IOS XE commands are entered in
  global configuration mode; a mode command applies to the statements after
  it, up to the next mode command or `exit`.
- A dash (**—**) in a command column means the fix text, Chapter 32, or the
  CLI Reference gives no command for the requirement; the setting column
  says why.

**Router fix text corrections.** The router fix texts were written for older
releases, and several were copied from the switch STIG. The crosswalk uses
these corrected commands:

- `CISC-ND-001410` answers the prompts of `copy run scp` with `pattern`
  arguments in four actions. The crosswalk uses the non-interactive form
  that Chapter 32 verified: `file prompt quiet`, `authorization bypass` on
  the applet, and one `copy running-config scp://...` action. Chapter 32's
  `ip scp server enable` is left out, because it turns on the router's own
  SCP server, which is not needed to copy to one.
- `CISC-RT-000120` is written with `SW1` prompts and five CoPP classes. The
  cell shows two of them (the critical and undesirable classes) with the
  fix text's policing values, renamed in capitals; build the other three
  the same way.
- `CISC-RT-000280` builds the alternate gateway filter but never applies
  it; the crosswalk adds `ip access-group FILTER_ISP in` on the interface to
  the alternate gateway. `CISC-RT-000290` only adds the static route; the
  crosswalk also removes the BGP neighbor, as its text says.
- `CISC-RT-000300` applies the route map to EIGRP redistribution. The saved
  references have no EIGRP command reference, so the crosswalk applies it to
  OSPF and BGP redistribution, which the requirement also names.
- `CISC-RT-000400` and `CISC-RT-000460` build an ISAKMP policy with no
  encryption or Diffie-Hellman group (so the defaults apply) and a transform
  set of `ah-sha256-hmac esp-aes`. `ah-sha256-hmac` is not in the Security
  Command Reference's list of allowed transforms, and `esp-aes` alone is
  128-bit AES. The crosswalk adds `encryption aes 256` and `group 20`, and
  uses `esp-gcm 256`, which provides encryption and integrity. IKEv2 is the
  better choice where both ends support it (Chapter 34).
- `CISC-RT-000410` uses the port name `snmp-trap` (the IOS keyword is
  `snmptrap`), and the `permit` article lists none of the port names it
  uses, so the crosswalk writes the ports as numbers (49, 22, 161, 162, and
  514). It also applies the ACL outbound on the interface to the NOC, which
  the fix text does not do.
- `CISC-RT-000420` configures `network 0.0.0.0 0.0.0.0 area 0`. A wildcard
  of 0.0.0.0 matches only the address 0.0.0.0, so no interface would join
  the area; the crosswalk uses the network and wildcard of each routing
  domain.
- `CISC-RT-000780` enters `no class class-default` at the class prompt
  before adding the class; it is left out. The policy is attached to the
  interface in the `CISC-RT-000760` row.
- The router fix for `CISC-ND-001370` writes `radius host` and `aaa
  authentication CONSOLE` without the `login` keyword, and the router fix
  for `CISC-ND-000010` adds `session-limit` under `line vty 0 4`. Both rules
  reuse the Chapter 32 commands, which use `radius server` and the `login`
  keyword and cover every VTY line.

### Where the version columns come from

The crosswalk table has a version column for each platform, and the IOS XE
column says which source each value comes from:

- **"(Chapter 32)"** marks a reused command. The value is the "First listed
  / Introduced (IOS XE)" entry of the Chapter 32 feature map row that
  supplies the command, which Chapter 32 built from the **Catalyst 9300**
  release notes for IOS XE 17.1.x through 26.2.x. `17.1.1 or earlier` means
  the feature predates the oldest release notes Chapter 32 used. IOS XE
  routers and switches share most of these commands, but release notes are
  per platform; check the router's release notes for a feature listed after
  17.1.1.
- **"(Command History)"** marks a command from the router fix text. The
  value comes from the "Command History" tables of the platform-independent
  IOS XE command references for access and edge routers, read for every
  statement in the cell. `IOS XE 2.1` (or 3.2S, and so on) is the first IOS
  XE row of the history; where a cell uses several commands, it is the
  latest of those first rows, so that every command in the cell is
  available. `Cisco IOS ..., no IOS XE row` means that no command in the
  cell has an IOS XE row: the history lists only classic Cisco IOS
  releases, from which IOS XE inherited the command, and the value is the
  latest first release among them. Where one command has no history (`match
  ip dscp`), the cell says so.
- **FortiOS version** is the "Introduced (FortiOS)" entry of the Chapter 30
  feature that the FortiGate setting uses. Chapter 30 built that column from
  the FortiOS New Features Guides for 7.0 to 8.0; `7.0.0 or earlier` marks a
  core platform feature that predates them.
- **Not in the Chapter 30 feature map (8.0.1 CLI Reference)** marks a
  FortiOS setting that comes only from the 8.0.1 CLI Reference, such as the
  multicast routing settings or the IPv6 extension header filter, so no
  first release is given; check the CLI Reference for your release.
- A dash (**—**) means the row has no command on that platform.

### Prerequisites

A FortiGate setting often meets its requirement only if something else is
already in place. A **prerequisite** is anything that must exist or be
configured *before* a row's FortiGate setting can meet the requirement:
the FortiCare registration and support contract, a FortiGuard subscription
and a path to FortiGuard, a model capability (a log disk), an external
server (LDAP, syslog, FortiAnalyzer, SMTP, NTP, an SNMP manager),
certificates and revocation services from the DoD PKI, an operating mode
(FIPS-CC mode, multi-VDOM mode), neighboring routers configured with
matching authentication keys, or an earlier setting the row depends on (an
administrator profile, a user group, a management interface, an IPsec
phase 1 interface, a PKI peer user, a firewall policy that applies the
profile). Settings that the row's own command creates are not listed
again, and neither are the FortiGate itself, its interfaces and routes,
and the policy table, which every row depends on. The prerequisites cover
**the FortiGate side only**.

The 26 prerequisites are Chapter 30's, with the same IDs, wording, and
commands, so that the map and the crosswalks agree; the build script checks
them against the *FortiGate prerequisites* table of Chapter 30. Only the
26 of Chapter 30's 48 that a row here needs are listed, so the IDs
are not consecutive. They are listed once in *FortiGate prerequisites*, and
the crosswalk and unmatched-requirement tables name the IDs each row needs
in their **FortiGate prerequisites** column:

- **Crosswalk rows.** A row whose FortiGate setting is a Chapter 30 feature
  takes that feature's IDs from Chapter 30 (71 rows). The
  34 rows whose setting comes from Chapter 34 show the same IDs as
  the Chapter 34 row. 2 rows differ from Chapter 30:
  `CISC-ND-001440` adds the FortiGate's own DoD certificate (P16), as
  Chapter 34 does for the same setting, and the firewall policy to the NOC
  tunnel (`CISC-RT-000410`) lists the IPsec tunnel it sends traffic into
  (P43). The IPsec tunnels to the NOC (`CISC-RT-000400` and
  `CISC-RT-000460`) set up certificate authentication in full, so they
  carry Chapter 30's certificate prerequisites; their own command creates
  the phase 1 interface. The 36 rows whose setting is not in the
  Chapter 30 feature map follow Chapter 30's rules: the BGP settings list
  the neighboring routers (P45), as Chapter 30's BGP rows do, the separate
  management OSPF instance also lists multi-VDOM mode (P47), and the
  interface, IPv6 extension header, traffic shaping, and multicast settings
  need nothing beyond the FortiGate.
- **Unmatched requirements.** Each row takes the IDs of the Chapter 30 row
  whose command it shows, so a requirement listed here and in Chapter 34
  has the same IDs in both. Chapter 30 shows the DoS policy command on two
  rows: the DoS policy protecting the management interface needs the
  management interface (P42), and the general DoS policies need nothing.

A dash means the setting needs nothing beyond the FortiGate, and the
30 rows with no FortiGate command, or that are Not supported or Not
applicable, always show a dash.

Fortinet publishes no FortiGate feature matrix in the documents Chapter 30
uses, so the **licenses** come from the FortiOS New Features Guides: the
FortiGuard service entitlements in *Update FortiGuard License Information
widget* (7.4.1), and the support contract and registration rules in
*Prevent FortiGates with an expired support contract from upgrading to a
major or minor firmware release* and the related 7.4 and 7.6 features. Here
they are the support contract (P1) on the firmware and update rows and the
Intrusion Prevention (P3), Advanced Malware Protection (P4), and Web
Filtering (P5) subscriptions on the IPS, antivirus, and web filter rows of
the unmatched requirements. **Model support** is given only where a guide
states it; the one such prerequisite here is the log disk that local disk
logging needs (P12). Check *System > FortiGuard*, the release notes, and the
hardware guides for your exact model and release before you plan on a
licensed or model-specific feature.

During an assessment, check a row's prerequisites before its setting: a
correctly configured setting with a missing prerequisite (BGP passwords
that the neighbor does not share, an IPsec tunnel to the NOC with no DoD
certificate on the FortiGate, a syslog setting with no TLS syslog server,
local disk logging on a model without a log disk) does not meet the
requirement, and the missing prerequisite is the finding.

### Alignment categories

Every row has one of six categories:

| Category | Meaning |
| --- | --- |
| Same requirement | Chapter 30 maps a FortiGate feature to the same SRG ID (directly, or through the FortiGate STIG rule that implements it), and the feature meets the requirement. |
| Equivalent setting | A FortiGate setting meets the requirement, although Chapter 30 did not map it to this SRG ID. |
| Partial | FortiGate meets part of the requirement. The setting column says what is missing. |
| Not supported | FortiGate has no such capability (for example MPLS, LDP, VPLS, GTSM, or an IP options filter), so it cannot meet the rule or take the role the rule secures. |
| Not applicable | The rule targets a component, role, or protocol that FortiGate does not have (an auxiliary port, Cisco Express Forwarding, an MPLS P router, MSDP), so there is nothing to secure. |
| By procedure | The requirement is met by a process rather than a setting, on both platforms (address planning). |

**Partial**, **Not supported**, and **Not applicable** take precedence over
**Same requirement**: where Chapter 30 maps the same SRG ID but FortiGate
does not fully meet it, the row is Partial and its setting cell notes that
Chapter 30 maps the requirement.

## Design Considerations

- **Decide each FortiGate's routing role first.** A branch or SD-WAN
  FortiGate that connects an enclave to a DoD network is a perimeter router,
  and the perimeter rules apply. The PE and P rules apply only where the
  FortiGate carries BGP VPNv4 routes for other networks, the OOBM rules
  only where it is the OOBM gateway, and the BGP, multicast, and MSDP rules
  only where those protocols run. Record the role on the checklist.
- **Use three checklists for one FortiGate.** The FortiGate NDM STIG for
  management (the FortiGate STIG rule column), the FortiGate Firewall STIG
  for policy, and a Router SRG-based checklist for routing, with the router
  rules as the guide to what to check.
- **Take the stricter value where the documents differ.** The router NDM STIG
  ends idle management sessions after **5 minutes**, as the SRG requires;
  the FortiGate NDM STIG allows **10**. The router STIG asks for two
  authentication servers and two syslog servers; the FortiGate STIG rules
  for the same SRG IDs ask for LDAP and one log server. Meet the router
  value on FortiGate.
- **Plan routing protocol authentication together.** OSPF with an
  HMAC-SHA-256 key chain works on both platforms. For BGP, both use a
  per-neighbor TCP MD5 password, which is not a FIPS 198-1 algorithm;
  FortiOS supports TCP-AO from 7.4.2 (Chapter 30), and Chapter 32 records
  that the IOS XE references it used do not document TCP-AO. Record BGP MD5
  as a finding where TCP-AO is not in use.
- **Do not plan an MPLS core on FortiGate.** FortiOS 8.0.1 has no MPLS, so a
  FortiGate cannot be an MPLS PE or P router. Keep the MPLS core on routers
  that support it, and use FortiGate VRFs and BGP VPNv4 over IPsec only for
  overlay segmentation.

router rule requires in plain language; the SRG ID links it to the
requirement text. The command columns follow the conventions in *Where the
commands come from*, the version columns those in *Where the version
columns come from*, and the prerequisite IDs refer to
*FortiGate prerequisites*.

checklist misses them: 25 FortiGate NDM STIG rules,
29 FortiGate Firewall STIG rules, 14 IDPS, 30
VPN, 22 ALG, and 4 Router SRG requirements. The Router SRG
requirements matter most for a routing FortiGate: disable non-essential
capabilities (`SRG-NET-000131-RTR-000035`), restrict traffic destined to
the router itself (`SRG-NET-000205-RTR-000001`), authenticate all control
plane protocols (`SRG-NET-000230-RTR-000001`), and use routing protocol
keys that last no more than 180 days (`SRG-NET-000230-RTR-000003`). The IOS
XE Router STIG covers these topics under other SRG IDs, but an SRG-based
checklist for a FortiGate needs them under their own. The FortiGate STIG
rules include the default password, FIPS-CC mode, LDAPS, and the audit
tool protection rules. Add them all to the FortiGate checklist. The requirement text is the FortiGate rule title or the
SRG title; the setting column lists the Chapter 30 features mapped to the
requirement, the version column gives the release of the feature whose
command is shown, and the prerequisite IDs are those of the Chapter 30 row
whose command is shown (see *FortiGate prerequisites*).

FortiGate meets 98 of the 139 router rules' requirements
with a setting (48 through the feature Chapter 30 maps and 50
through another setting), 14 only in part, and cannot meet 17;
9 rules target something FortiGate does not have, and 1 is met
by procedure. **36 of the 139 router rules have a
FortiGate STIG rule for the same SRG requirement** (all 36 of
them NDM rules, matching 35 distinct FortiGate rules);
the 97 RTR rules have none, because no FortiGate STIG covers routing.
The main differences:

- **The NDM rules align closely.** 36 of the 42 NDM rules
  pair with a FortiGate NDM STIG rule, and all but two are met with a
  setting. The two Partial rows: FortiOS 8.0.1 has no option for changed
  characters in administrator passwords (`CISC-ND-000610`; Chapter 30
  records the same gap for `FGFW-ND-000311`), and the 8.0.1 CLI Reference
  documents no setting for how administrator passwords are stored
  (`CISC-ND-000620`).
- **Where the Cisco router is stricter.** IOS XE can drop packets with IP
  options (`CISC-RT-000350`, `CISC-RT-000750`), stop ICMP unreachable and
  mask reply messages, check the TTL of BGP packets (GTSM,
  `CISC-RT-000470`), filter IPv6 extension headers by type with a permit for
  Routing header type 2, filter PIM Join messages and IGMP and MLD reports
  per interface, and limit IGMP state per interface. FortiOS 8.0.1 has none
  of these, or only part. The IPv6 extension header filter blocks whole
  header types or up to seven option types:

  FortiOS: `config firewall ipv6-eh-filter; set hop-opt enable; set routing enable; end`

- **Where FortiGate is stricter or simpler.** Every FortiGate firewall policy
  ends in an implicit deny and logs denied traffic when asked, so the
  perimeter filtering rules are met by policies rather than by ACLs written
  for each interface. FortiGate syslog can use reliable TCP with TLS, where
  the router rule asks only for two `logging host` destinations, and the
  FortiGate STIG has rules, such as FIPS-CC mode and LDAPS, that no router
  rule matches (second table).
- **MPLS and MSDP.** FortiOS 8.0.1 has no MPLS, LDP, RSVP-TE, VPWS, or VPLS,
  so 17 rules are Not supported, mostly the MPLS rules; the VRF,
  route distinguisher, and route target rules are Partial because FortiGate
  supports them only for BGP VPNv4 over IPsec. FortiOS does not run MSDP,
  so the six MSDP rules are Not applicable, but it does run PIM sparse mode
  with a rendezvous point, register filters and rate limits, and an SPT
  threshold, so the RP and DR rules are met or partly met.
- **Alternate gateway and OOBM rules.** The router-only rules for an
  alternate gateway and an OOBM gateway are met with firewall policies,
  static routes, route maps, local-in policies, VDOMs, and IPsec tunnels to
  the NOC.

## Validation and Troubleshooting

- **A router rule seems to have no row.** Every one of the 139 rules
  has a row; the build script fails if one is missing. Search for the rule
  ID, not the title.
- **A router fix text command is rejected.** Check *Router fix text
  corrections*: `ah-sha256-hmac`, `snmp-trap`, and `cpp system-default` on a
  router are the common cases. Use `?` on the CLI.
- **An assessor asks for the FortiGate STIG rule for an RTR rule.** There is
  none; show the Router SRG requirement in the SRG ID column, as Chapter 30
  maps it, and the FortiGate setting from the table.
- **A FortiGate in an MPLS design.** A FortiGate cannot be the MPLS PE or P
  router; mark the MPLS rules Not supported, keep the MPLS core on the Cisco
  routers, and use FortiGate VRFs and BGP VPNv4 over IPsec only for overlay
  segmentation.
- **BGP sessions to a FortiGate lack GTSM.** Mitigate with a local-in policy
  that accepts BGP (TCP port 179) only from the configured peer addresses,
  and record the gap.

## Security and Best Practices

- Treat the router STIG rules as the routing checklist for every router, and
  add the FortiGate-only requirements and the FortiGate STIG rules for each
  FortiGate.
- On both platforms, end idle management sessions after 5 minutes, lock
  accounts after three failed logons, show the DoD banner, require
  15-character passwords, and allow management only over SSH and HTTPS from
  authorized networks or a dedicated management interface.
- Authenticate OSPF with HMAC-SHA-256 key chains, use a unique key for each
  BGP peer, filter bogon and own prefixes, and limit the prefixes accepted
  from each peer.
- At the perimeter, deny by default, block bogon sources, check source
  addresses, and block outbound management traffic.
- Record every Partial and Not supported row as an open finding with its
  mitigation, and review the crosswalk whenever DISA updates the router or
  FortiGate STIGs or the Router SRG, or a new IOS XE or FortiOS release
  changes the commands.
