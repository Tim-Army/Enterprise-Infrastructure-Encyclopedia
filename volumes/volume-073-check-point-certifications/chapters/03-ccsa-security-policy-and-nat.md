# Chapter 03: CCSA — Security Policy and NAT

## Learning Objectives

- Build an Access Control policy with rules, layers, and objects.
- Configure Automatic and Manual NAT.
- Install policy and read the logs in SmartConsole.
- Understand implied rules and the cleanup rule.
- Complete a walkthrough for each policy topic.

## Theory and Architecture

The **Access Control policy** is an ordered rule base of **objects** — each rule matches on source,
destination, service, and (optionally) application/content, and takes an **action** (Accept, Drop,
Reject). Rules are evaluated **top-down, first match wins**, so specific rules precede general ones,
and an explicit **cleanup rule** (Any/Any/Drop with logging) sits at the bottom to log what nothing
else matched. **Implied rules** (generated by the gateway for control traffic) run around the
explicit base. Policy can be split into **layers** (ordered or inline) for delegation and
readability. **NAT** translates addresses: **Automatic NAT** (a checkbox on a host/network object —
Hide behind the gateway for outbound, or Static for one-to-one) covers most cases; **Manual NAT**
(explicit NAT rules) gives fine control. Changes are staged in the database and take effect on
**Install Policy**, which compiles and pushes the rule base to the gateway. **Logs** in SmartConsole
show each connection against the matching rule — the core of CCSA operations.

## Design Considerations

Order rules **most specific first**; end with an explicit **cleanup rule** that logs. Use **objects**
(not raw IPs) and **groups** for maintainability. Prefer **Automatic Hide NAT** for outbound and
**Static NAT** for published servers; reserve **Manual NAT** for exceptions. **Log** meaningful
rules. Use **layers** to delegate policy sections.

## Validation and Troubleshooting

Confirm policy processing:

```text
Access rules: top-down, first match wins -> Accept/Drop/Reject. Specific first; explicit cleanup rule (Any/Any/Drop, log) last.
Implied rules run around the explicit base. NAT: Automatic (Hide=outbound, Static=1:1) vs Manual (explicit rules).
Changes take effect on Install Policy. Logs show connection -> matching rule.
```

Common pitfalls: no **cleanup rule** (silent drops, no logs); and forgetting to **Install Policy**
(edits stay in the database, unenforced).

## Security and Best Practices

Least privilege: specific rules, explicit **cleanup rule** with logging, **objects/groups**, and
**layers** for delegation. Prefer Automatic NAT; log meaningful rules; **install policy** to enforce.
Review the rule base regularly. Defensive administration.

## Hands-On Lab

Policy walkthroughs. **Shared prerequisites** — Check Point management + gateway (SIC established),
SmartConsole. **Cost:** none.

### Lab 3.1 — Create an Access Control rule

**Objective:** Add a least-privilege rule.

```text
# SmartConsole -> Security Policies -> Access Control -> add rule:
#   Source: Internal_Net  Destination: Web_Server  Service: https  Action: Accept  Track: Log
"rule: Internal_Net -> Web_Server : https : Accept + Log (specific, above the cleanup rule)"
```

**Expected result:** a specific, logged Accept rule — least-privilege access.

**Negative test:** put an **Any/Any/Accept** rule at the top; it shadows everything below — order
specific rules first.

**Rollback:** delete the lab rule.

### Lab 3.2 — Add the cleanup rule

**Objective:** Log everything unmatched.

```text
# Bottom of the rule base:
#   Source: Any  Destination: Any  Service: Any  Action: Drop  Track: Log  Name: Cleanup
"cleanup rule: Any/Any/Any Drop + Log -> the last, explicit rule"
```

**Expected result:** an explicit **cleanup rule** — unmatched traffic is dropped **and logged**.

**Negative test:** rely on the invisible implicit cleanup (no log); add an **explicit** logged
cleanup rule — you need the logs.

**Rollback:** keep the cleanup rule (best practice).

### Lab 3.3 — Configure Automatic Hide NAT

**Objective:** NAT internal hosts outbound.

```text
# Object: Internal_Net -> NAT tab -> Add automatic address translation -> Hide -> behind the gateway.
"Automatic Hide NAT: Internal_Net hidden behind gateway IP for outbound Internet"
```

**Expected result:** internal hosts reach the Internet **hidden** behind the gateway — Automatic
Hide NAT.

**Negative test:** publish an internal server with **Hide** NAT (inbound fails); use **Static** NAT
for inbound-reachable servers.

**Rollback:** disable the lab NAT.

### Lab 3.4 — Install policy

**Objective:** Enforce the changes.

```bash
# SmartConsole -> Install Policy (or via Management API):
mgmt_cli install-policy policy-package "Standard" access true threat-prevention false -s id.txt 2>/dev/null \
  || echo "Install Policy compiles the rule base and pushes it to the gateway -> now enforced"
```

**Expected result:** policy **installed** — the gateway now enforces the new rules and NAT.

**Negative test:** edit rules and skip **Install Policy**; nothing changes on the gateway — install
to enforce.

**Rollback:** None — read-only; this lab changes no persistent state, so there is nothing to revert.

### Lab 3.5 — Read the logs

**Objective:** Verify with logs.

```text
# SmartConsole -> Logs & Monitor -> Logs: filter by rule/source; confirm the new rule matches.
"logs: connection -> matched rule (name/number) -> Accept/Drop; verify least-privilege is working"
```

**Expected result:** log entries mapping connections to the **matching rule** — policy verified.

**Negative test:** assume a rule works without checking logs; the **logs** are the evidence — read
them.

**Rollback:** none (read-only).
