## Theory and Architecture

This is the volume's **as-built chapter**. Like an as-built drawing, it
records how the volume was actually made rather than how it was planned: which
parts were generated by a repeatable workflow, which sources each part rests
on, and which changes came later. It is numbered 90 so that it stays last if
chapters are added, and so that as-built chapters have the same number in every
volume that has one.

The three content chapters were not written here. They were built inside
[Volume CLXXII — DISA SRGs and STIGs](../../volume-172-disa-srgs-and-stigs/README.md)
as Chapters 11, 33, and 37, by the `/srg-mapping-for` workflow that
[Volume CLXXII's own as-built chapter](../../volume-172-disa-srgs-and-stigs/chapters/90-as-built-how-this-volume-was-built.md)
describes step by step. On 2026-11-04 they moved here, together with their CSV
files and the SRG mapping workbook, because volume numbers 200 to 299 are
reserved for Fortinet STIG work (see [Structure.md](../../../Structure.md)) and
FortiSwitch was chosen as the first volume of that block. This chapter records
only what is specific to the FortiSwitch material. For the workflow itself
(inventory, agents, playbooks, registration), read the Volume CLXXII chapter.

## Design Considerations

- **The SRG ID is the join key.** Every STIG rule names the SRG requirement it
  implements (the XCCDF Group title). A FortiSwitch row with the same SRG ID is
  "Same requirement". For the other rules the agent looked for the setting that
  meets the same requirement in the FortiSwitchOS CLI Reference. CCI matches
  were not used without reading the requirement text, because the catch-all
  CCI-000366 links unrelated requirements.
- **Every rule appears.** Chapter 02 has one row for each of the 152 Cisco IOS
  XE Switch STIG rules and Chapter 03 one for each of the 142 NX-OS Switch
  rules. A second table in each lists the FortiSwitch requirements that no
  Cisco rule cites.
- **Commands are machine-checked.** Every FortiSwitchOS command was tested
  against the extracted CLI Reference text: the command path must exist, each
  option must exist in that context, and each literal value must be documented.
  A dash means no verified setting was found, not that the requirement is met.
- **Versions come from the vendor's own documents.** FortiSwitch versions come
  from the 29 published feature matrices, 7.0.0 through 8.0.0. "First listed"
  is not the same as "introduced": a few features existed before Fortinet added
  them to the matrix.
- **Chapters 02 and 03 agree.** The two crosswalks share one prerequisites
  list (the same IDs, wording, and commands), and a reused FortiSwitch row must
  match Chapter 02's row for the same rule.
- **The workbook is a working copy.** It is not generated from the chapters.
  The chapters keep their original FortiSwitchOS 8.0.0 command verification;
  the workbook adds a FortiSwitchOS 7.6.7 documentation baseline.
- **The Milestone-1 sheet is left alone.** That sheet takes only the
  crosswalk and minimizes the information. Additions go to the crosswalk sheet,
  `Fortiswitch vs Cisco`.

## Implementation and Automation

### The crosswalk method for Chapters 02 and 03

For each reference rule, the agent followed `CROSSWALK-PLAYBOOK.txt`:

1. Read the rule, its SRG ID, and its fix text. Rules that cite an SRG ID
   retired from current SRGs are pointed at the current requirement for the
   same topic.
2. Look for the same SRG ID in the FortiSwitch map (Chapter 01).
3. If none, find the FortiSwitch setting that meets the same requirement in the
   FortiSwitchOS CLI Reference, and record its command and the first release
   that lists the feature.
4. Judge how well the setting meets the requirement and assign one of six
   alignments: Same requirement, Equivalent setting, Partial, Not supported,
   Not applicable, or By procedure.
5. Add the prerequisite IDs the setting needs (a license, a model, an operating
   mode, an external server).
6. Verify the command and fail the build if a reference rule is missing or
   duplicated.

Chapter 03 added one step: where the NX-OS rule has the same ID, SRG ID, and
title as an IOS XE rule, it takes Chapter 02's FortiSwitch side unchanged.

### The workbook, step by step

The workbook,
`data/01-fortiswitch-feature-version-and-srg-map-feature-map-20261103.xlsx`,
began as a hand-filled sheet that maps FortiSwitch features to SRG
requirements. It was changed in these steps on 2026-11-04. Backups of the
workbook were kept outside the repository before each change.

1. **FortiSwitchOS 7.6.7 baseline.** The comments were rewritten to reflect
   7.6.7, references to version 8 were corrected, and the 13 features that the
   7.6.7 Feature Matrix does not list were tagged "Not in 7.6.7". The DCBX
   rows were marked as present only in version 8 and later.
2. **Model support.** Every feature was checked against the Feature Matrix
   columns for the two target models, FS-648F-FPOE and FS-2048F. The result is
   the `Model Support 7.6.7` sheet (235 features), also written to CSV.
3. **The AI-comments column.** A column in the crosswalk sheet holds notes on
   each row: what was checked, what differs from the chapters, and what still
   needs a person. It is separate from the user-entered columns.
4. **The "x" marker.** An "x" means the feature was found in the
   documentation but has not been verified in the CLI or the GUI. When the CLI
   or GUI verification columns are filled in, the row counts as verified. The
   "CLI Verified by" column records that the command syntax was verified.
5. **Migration of 286 features.** The features listed on the separate
   `Fortiswitch` sheet were added to the crosswalk sheet (rows 154 to 437),
   each with "Nobody" as its CLI and GUI verifier, and the `Fortiswitch` sheet
   was then removed.
6. **Reference and Page.** For the added rows, the Reference and Page columns
   were filled from the FortiSwitch 7.6.7 Feature Matrix, the FortiSwitchOS
   7.6.7 CLI Reference and Administration Guide, and the FortiOS 7.6.7 CLI
   Reference (for FortiGate commands). A locator script found the PDF page.
   For the two CLI references and the Administration Guide the printed page
   equals the PDF page. Rows with no page are noted in the AI-comments
   column.
7. **SRG IDs and versions.** The SRG IDs were parsed from the SRG rule lists on
   Cyber Trackr, a third-party mirror, and compared with the workbook. The
   versions matched were Layer 2 Switch SRG V3R4, Network Device Management SRG
   V5R5, Router SRG V5R2, and AAA Services SRG V2R3. Every ID still needs
   confirmation against DISA's own files, and the workbook notes which rows.
8. **Decisions.** The Router SRG applies (the licensed Layer 3 features are in
   scope), AAA Services requirements are inherited from the authentication
   system rather than met on the switch, and the FortiGate prerequisite P7
   stays on the list. Prerequisites that a row requires were added, bringing
   the list to 17 (P1 to P17).

### Reference and Page columns in Chapters 01 to 03

Chapters 01, 02, and 03 have Reference and Page columns that say where each
FortiSwitchOS command is documented: the FortiSwitchOS 7.6.7 CLI Reference, the
7.6.7 Administration Guide (Standalone Mode), or the FortiLink Guide (FortiOS
7.6.7), with PDF page numbers. They came from the feature-map workbook the user
filled in on 2026-10-26. A locator script found pages for the remaining
commands, the user's own page choices were applied to the same commands in all
three chapters, and a consistency check confirmed that each command has one
Reference and Page everywhere.

Where the 7.6.7 documents disagree with the chapter's command (for example
`detect-ip-conflict`, which the CLI Reference syntax prints with underscores),
the chapter notes the difference. These changes keep the chapters' existing
rows and commands. They are not part of the skill, so a rebuild from an agent's
original pipeline would not reproduce them.

### The CSV files and the interactive table

Two scripts write the downloads:

```bash
python scripts/python/export_srg_tables.py
python scripts/python/export_srg_workbook.py
```

`export_srg_tables.py` finds each table in Chapters 01 to 03 by its heading and
writes it to `data/<chapter>-<suffix>.csv`, then inserts or refreshes the
download link on the line before the table. `export_srg_workbook.py` reads the
workbook with `openpyxl` and writes three CSV files, one each for the
crosswalk (438 rows, 20 columns), prerequisites (17 rows), and model support
(235 rows). It also fills `scripts/python/srg_workbook_page.html.tpl` to
produce `publishing/interactive/fortiswitch-srg-crosswalk.html`, a
self-contained page with search, filters (severity, SRG, origin, CLI
verified), sortable columns, a column chooser, row detail, and download
buttons for the filtered rows or the whole sheet. The CSV files use UTF-8 with
a byte-order mark and CRLF line ends, like the other CSV files in the
repository, so spreadsheet programs show dashes and quotes correctly.

`scripts/bash/build-download-site.sh` copies the page to the portal at
`interactive/` and the CSV files to `data/volume-201-fortiswitch-stig-and-srg-mapping/`,
and links the page on the portal's front page. The Excel workbook itself is
published only in the repository, not on the portal.

## Validation and Troubleshooting

To check this volume:

- **Row counts.** Chapter 01 has 235 feature rows, Chapter 02 has 152
  crosswalk rows, and Chapter 03 has 142. The CSV files must match: run
  `python scripts/python/export_srg_tables.py` and confirm a clean `git status`
  afterward.
- **Workbook exports.** Run `python scripts/python/export_srg_workbook.py`. It
  should report 438 crosswalk rows, 17 prerequisites rows, and 235
  model-support rows, and leave the generated page unchanged if the workbook
  has not changed.
- **Repository checks.** `scripts/bash/validate.sh` checks `book.yml`, internal
  links, markdownlint, and cspell. The `imports/` folder is not tracked, and
  its local files can fail the spelling check without affecting the volume.

Common problems:

| Symptom | Cause | Fix |
| --- | --- | --- |
| A link to a CSV file returns 404 on the portal | The link uses the Volume CLXXII path or an old file name | Run `export_srg_tables.py` to refresh the link |
| The interactive page shows old data | The workbook changed but the page was not regenerated | Run `export_srg_workbook.py` and commit the page and the CSV files |
| A reader lands on a short page at Chapter 11, 33, or 37 of Volume CLXXII | They followed an old link | The page links to the new chapter; nothing to fix |
| The workbook loses a data-validation rule after a script run | `openpyxl` drops the data-validation extension on save | Edit the workbook in Excel, or patch the XML; use `openpyxl` only to read it |

## Security and Best Practices

- **Treat "x" and a blank verifier as unverified.** A feature found in the
  documentation is not a verified setting until someone runs the command or
  checks the GUI and records it.
- **Confirm SRG IDs and versions with DISA.** The comparison used a
  third-party mirror. Download the SRG files from DoD Cyber Exchange before
  citing an ID in an authorization package.
- **Confirm prerequisites for your exact model and release.** Licenses and
  hardware support differ by model. The Advanced Features License is required
  for the Layer 3 features, and the FS-648F-FPOE and FS-2048F do not support
  every feature.
- **Do not commit the downloaded PDFs.** The `imports/` folder holds Fortinet
  documents and is not tracked.
- **Keep this chapter current.** When the workbook, a script, or a chapter
  changes, update this chapter in the same commit.
