You are writing ONE crosswalk chapter that aligns every rule of one vendor's
STIG package (the "reference" product, for example Cisco ASA) with the setting
on a comparable product from another vendor (the "comparison" product, for
example FortiGate) that meets the same SRG requirement.

Model chapter (read it first and copy its structure, wording, and conventions):
  volumes/volume-172-disa-srgs-and-stigs/chapters/33-fortiswitch-and-cisco-catalyst-switch-stig-crosswalk.md
Its build scripts, if still present, are in temp/xwalk/ (load.py, build.py,
verify.py, fswblocks.py, chapter-template.txt) and are good models.

HOW THE ALIGNMENT WORKS
- Every STIG rule names the SRG requirement it implements (the XCCDF Group
  title, for example SRG-APP-000190-NDM-000267). Align through that ID.
- The comparison product's settings come from its map chapter in this volume
  (the coordinator names it). A comparison row with the same SRG ID is "Same
  requirement". For the rest, find the comparison product's setting that meets
  the same requirement yourself, in its command reference.
- Do not use CCI matches without reading the requirement text: the catch-all
  CCI-000366 links unrelated requirements.
- Some rules cite SRG IDs retired from the current SRG releases. Say so, and
  point the row to the current requirement for the same topic.
- If the comparison product has its own STIG (FortiGate does), add a column
  for the comparison STIG rule that implements the same SRG ID, and count
  matches in the summary.

SOURCES

  (temp/cisco/stigs.json for Cisco: id, severity, srg, title, fix text) and the
  unzipped XCCDF folder.
- Reference product commands: if a map chapter for the reference product exists
  (for example Chapter 32 for Cisco IOS XE switches), reuse its verified
  commands for the same rule IDs. Otherwise start from each rule's fix text and
  CHECK it against the vendor's command references (cisco.com returns HTTP 403
  to curl, so read pages through the built-in browser, mcp__Claude_Browser__*,
  and save what you read as JSON or text in your scratch folder). DISA fix text
  often contains syntax that does not parse; correct it and list every
  correction in the chapter.
- Reference product versions: the release in which each command was introduced,
  from the "Command History" table of the command's entry in the vendor's
  command reference. If a command entry has no history, say which reference
  release it was verified in. Do not guess.
- Comparison product settings, commands, and versions: its map chapter and CSV
  (data/<chapter>-feature-map.csv) and the command reference text the
  coordinator names. The version is the map chapter's version column for the
  feature used; settings not in that product's version source read
  "Not in the <source> (<release> CLI Reference)", never a guessed release.

WHAT TO BUILD
1. "### The crosswalk table": one row per reference rule (ALL of them, grouped
   by STIG), columns:
   | <Ref> rule | Severity | SRG ID | Requirement | <Ref> command | <Ref> version | <Cmp> setting | <Cmp> command | <Cmp> version | Alignment |
   plus "<Cmp> STIG rule" after "SRG ID" when the comparison product has a STIG.
   Alignment is one of: Same requirement, Equivalent setting, Partial (say
   what is missing), Not supported (say so), Not applicable (the rule targets a
   role, protocol, or component the comparison product does not have), or By
   procedure. Define them in the chapter, as Chapter 33 does.
2. "### <Cmp> requirements with no <Ref> rule": the comparison product's mapped
   requirements that no reference rule cites, with its setting, command, and
   version.
2b. "### <Cmp> prerequisites": the comparison product's prerequisites table,
   placed just before "### The crosswalk table", plus a "<Cmp> prerequisites"

3. "### Alignment summary": counts by STIG and category, and prose on the main
