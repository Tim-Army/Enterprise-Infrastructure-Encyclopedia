STEP 1. Sources (download into temp/<product-slug>/)
- Vendor documentation sites are often JavaScript-rendered. Try curl first; if
  it fails, use the built-in browser (mcp__Claude_Browser__navigate +
  javascript_tool) to find document pages and their PDF links, then download
  with curl -sSfLO. Table-of-contents HTML pages often give full, untruncated
  feature titles. If a PDF is blocked (HTTP 403), use the online pages and say so.
- Version source, in order of preference:
    a) a per-release feature matrix, or
    b) a New Features Guide (or "What's new" document) per release train, or
    c) the release notes' "What's new / New features" sections, or
    d) the administration guide table of contents for the oldest and newest
       train (only if nothing better exists; say so in the chapter).
  Cover every release train the vendor still publishes, from the oldest current
  train to the newest. Say exactly which documents and releases were used.
- Command source: the newest CLI or command reference. If the product has no
  CLI reference (GUI-only or a cloud service), say so and use "GUI: <pane>"
  entries checked against the administration guide.
- Requirement source: unzip the needed STIG or SRG ZIPs from the newest dated
  DISA library folder under imports/ into temp/<product-slug>/ (unless the
  coordinator says they are already unzipped elsewhere) and parse the XCCDF
  (Group/Rule/version = rule or requirement ID; severity high/medium/low =
  CAT I/II/III; Group title = the SRG ID a STIG rule implements; title).

STEP 2. Feature list
- Listed features: every feature from the version source, with truncated
  titles repaired, sub-topics folded into their parent feature, and duplicates
  across trains merged (version entries like "7.4.3+; 7.6.0+").
- Core platform features (category "Core: ..."): the long-standing capabilities
  the requirements depend on but that predate the oldest source (management
  access, administrator accounts and roles, remote authentication, password
  policy, lockout, idle timeout, banner, logging, NTP, SNMPv3, FIPS mode,
  certificates, backups, firmware, high availability, plus the product's main
  functional capabilities), dated "<oldest release> or earlier".
- The version column's wording must match the source ("First listed" for a
  feature matrix, "Introduced" for a New Features Guide or release notes).
  Explain the version-entry formats in a small table.

STEP 3. Requirement mapping
- STIG products: map to the STIG rules. EVERY rule in the product's STIG(s)
  must appear in the map, attached to the feature that satisfies it; make the
  build script fail if any rule is unmapped. The requirement reference table
  has an extra column for the SRG ID each rule implements:
  | STIG | Rule | Severity | SRG ID | Rule title |.
- SRG products: map to the SRGs the coordinator names (and only those, unless a
  clearly better one exists in the library; justify it in the chapter).
  Reference table: | SRG | Requirement | Severity | Requirement title |.
- Three relationship kinds: implements, must be configured to meet, or no
  direct requirement (NONE). NONE rows render as "No direct requirement; if
  unused, disable (<ABBR> `<non-essential-capabilities rule or requirement>`)",
  using the rule or requirement the coordinator names, and the chapter says
  which it is.
- Use abbreviations in the requirement column and define them in the chapter.
- The reference table lists every ID used in the map or cited in the prose.

STEP 4. Commands
- One command cell per feature: the command that configures it to meet the
  mapped requirement; for NONE rows, the command that disables it if unused;
  "GUI: <pane>" for GUI-only settings; or "—" when there is nothing to
  configure. Statements separated by "; ", placeholders in <ANGLE_BRACKETS>,
  backticks around commands. Never put a raw "|" inside a table cell.
- For a STIG rule, the rule's fix text is the starting point, but CHECK it
  against the vendor's command reference: DISA fix text sometimes contains
  syntax that does not parse or has been removed from newer releases. Use the
  correct current syntax and document every correction in the chapter.
- VERIFY every command automatically against the extracted command reference
  with a script: every command path or mode must exist, every option must exist

  verifier with deliberately wrong commands to prove it catches them. Fix every
  failure, or replace the command with an honest "—" or "GUI:" entry.
- Document product limitations (requirements the product cannot meet exactly
  with its own settings) in the "Where the commands come from" section, each
